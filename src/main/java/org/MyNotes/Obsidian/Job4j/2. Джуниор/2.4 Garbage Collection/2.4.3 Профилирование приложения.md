
**==Инструменты анализа памяти==**

**jps**

Каждая ваша программа на Java (и не только ваша) запускается в отдельной JVM как отдельный процесс в системе.
Поэтому, прежде чем профилировать приложение, нужно узнать его pid (сокр. от proccess id)


**jmap**

Эта утилита позволяет увидеть какие объекты созданы, какие ожидают удаления, т.е. объекты имеющие непосредственное отношение к памяти.
Также может сделать дамп памяти, т.е. сохранить ее состояние, как бы "сфоткать" ее.


**jstat**

В отличии от предыдущих утилит, утилита jstat предоставляет сводную информацию о состоянии памяти программы.
Она делает сэмприлование, т.е. периодически получает данные о состоянии разных участков памяти и их обобщает.

**==Доп инфа==**


**постоянный Full GC** — приложение почти не работает, только собирает мусор -> Производительность низкая из-за частых Stop-The-World пауз

 **цикл смерти**: Young (0.05ms) → Full (10-15ms) → Young → Full → ... -> **признак критической нехватки памяти** — молодое поколение не может ничего собрать, и всё ложится на Full GC.


## 1. **Allocation Failure** (Serial, Parallel, G1)

**Что это**: Попытка выделить объект в куче, но свободного места недостаточно.

**Простыми словами**: Приложение говорит "дайте мне память под новый объект", а GC отвечает "свободного места нет, нужно срочно собирать мусор".


## 2. **Ergonomics** (Parallel GC)

**Что это**: Автоматическая адаптация GC под нагрузку. JVM сама решает, когда запускать GC.

**Простыми словами**: "Чувствую, что пора собирать мусор, даже без Allocation Failure".


## 3. Типы пауз в G1 GC

### **(Normal) (G1 Evacuation Pause)**

**Что это**: Обычная молодая сборка. Объекты копируются (эвакуируются) из Eden в Survivor или Old.

### **(Concurrent Start) (G1 Evacuation Pause)**

**Что это**: Специальная молодая сборка, которая **запускает Concurrent Mark** (параллельную разметку).

### **(Prepare Mixed) (G1 Evacuation Pause)**

**Что это**: Подготовка к смешанной сборке (Mixed GC). G1 готовится собирать не только молодые, но и старые регионы.

### **(Mixed) (G1 Evacuation Pause)**

**Что это**: Сборка **и молодых, и старых** регионов одновременно.




## 4. Типы сборок в ZGC

### **Garbage Collection (Allocation Rate)**

**Что это**: ZGC запускается автоматически, когда видит **высокую скорость выделения памяти**.

### **Garbage Collection (Proactive)**

**Что это**: Проактивная сборка. ZGC запускается, даже если памяти еще достаточно.

### **Garbage Collection (Allocation Stall)**

**⚠️ САМЫЙ ВАЖНЫЙ И ОПАСНЫЙ**

**Что это**: Приложение не может выделить память и **ОСТАНАВЛИВАЕТСЯ**, ожидая, пока GC освободит место.

### **Garbage Collection (Warmup)** — ZGC

**Что это**: Первые сборки при запуске, когда ZGC калибруется.

==**Утечки памяти**==

В Java память расходуется нерационально чаще всего из-за невнимательности к структурам данных, области видимости объектов и особенностям работы JVM. Вот типичные ошибки:

## 1. Удержание ссылок на ненужные объекты (Memory Leaks)

- **Необнуление ссылок** в долгоживущих коллекциях (особенно в `static` полях).  
    Пример: `static List<Data> cache = new ArrayList<>();` без очистки.
    
- **Слушатели и колбэки**, которые не удаляются (GUI, события).
    
- **Внутренние классы** неявно ссылаются на внешний класс → сборщик мусора не может удалить большой внешний объект.
    

## 2. Неэффективное использование строк

- **Конкатенация в цикле** через `+` (создаётся много промежуточных `String`).  
    Правильно: `StringBuilder`.
    
- Использование `String.substring()` в старых версиях Java (до 7u6) – она держала ссылку на исходный массив `char[]` целиком.
    
- Хранение больших строк в `String` вместо `byte[]` или `char[]` (например, для бинарных данных).
    

## 3. Избыточное создание объектов

- **Автоупаковка (autoboxing)** в циклах:  
    `for (Integer i : list) sum += i;` → создаются `Integer` объекты.
    
- **`String.format()`** вместо простой конкатенации.
    
- Создание **временных объектов** внутри часто вызываемых методов (например, `new Date()` для логов).
    

## 4. Неправильные коллекции

- **`HashMap` с малым initial capacity** → частые rehash.
    
- **`ArrayList` с большим запасом** → лишняя память, или наоборот – маленький начальный размер → частые копирования.
    
- Использование `LinkedList` для хранения тысяч элементов, если нужен только доступ по индексу (высокие накладные расходы на узлы).
    
- Хранение **`null`** в коллекциях (занимает место ссылки, но не даёт выигрыша).
    

## 5. Неправильное использование кэшей

- **Бесконечный рост кэша** без политики вытеснения (`WeakHashMap`, `SoftReference`, `CacheBuilder`).
    
- Кэширование **легко вычисляемых** данных.
    
- Кэширование **всех результатов** без учёта времени жизни.
    

## 6. Проблемы с массивами

- Создание **двумерного массива** как `new int[n][n]`, когда достаточно `new int[n*n]` – лишние объекты-массивы строк.
    
- **Массивы объектов** вместо массивов примитивов (больше памяти + автоупаковка).
    

## 7. Статические поля, ссылающиеся на большие данные

java

public class Cache {
    private static List<byte[]> hugeData = new ArrayList<>(); // никогда не освободится
}

## 8. Использование `finalize()` (особенно старый код)

Объекты с `finalize()` живут дольше, т.к. требуют как минимум двух циклов GC.

## 9. Неправильные пулы потоков

- Создание **нового потока** на каждую задачу → память на стек потока (~1 МБ) и контекст.
    
- `Executors.newCachedThreadPool()` без лимита при высокой нагрузке.
    

## 10. Игнорирование примитивов

Хранение `Long` вместо `long`, `Boolean` вместо `boolean` в больших объёмах (разница в 8-16 байт на объект + заголовок).

## Как обнаружить?

- **JProfiler / YourKit** – анализ heap dump.
    
- **JConsole / VisualVM** – мониторинг памяти.
    
- **Ежедневный профилинг** в тестовой среде с реальными данными.
